# Security Rules

Purpose: protect document access, shared sessions, invitation proofs, private assets, signing workflows, and public verification from browser-side exposure or privilege confusion.

## Security Model

The frontend is untrusted. It may present state and collect intent, but the backend must authenticate, authorize, validate document state, enforce invitation gates, perform signing, and record immutable evidence.

For each security-sensitive change, identify:

- the authoritative service;
- the credential and cookie path;
- the resource and permission being checked;
- whether a token, identifier, document, image, or signature artifact is exposed;
- replay, stale-state, duplicate-submit, and ambiguous-failure behavior;
- the expected audit or signature evidence.

## Sessions And Cross-App Handoff

- `app/app` and `api/auth` own production identity and shared-session issuance.
- Browser code validates shared sessions through same-origin route handlers such as `/api/session`, `/api/me`, `/api/refresh`, and `/api/logout`.
- Never add production code that reads a refresh token from `document.cookie`.
- `session_active` is a non-sensitive routing hint, not proof of authentication, expiry, identity, or permission.
- Keep readable-cookie compatibility behind explicit development-only flags.
- Use hard navigation for cross-origin login, identity verification, Profile, and Settings handoffs.
- Send credentials only to configured Gracon origins; never derive an upstream origin from a query parameter.
- Logout must use the documents `/api/logout` path before returning to the local login route.

## Document Access

- `api/documents` is authoritative for owner, collaborator, invitation, permission, finalisation, signing, locking, and public verification access.
- Client permission checks control affordances only.
- Route possession, document ids, invitation tokens, cached metadata, or previously loaded content never grant continued access.
- Handle 401, 403, 404, 409, and gone/revoked states distinctly.
- Clear document content, collaborator data, sensitive previews, and caches when session identity or document access changes.
- Do not retain a readable document after an authoritative access-revoked response.
- Lists, comments, versions, activity, and audit data must be bounded and authorized independently.

## Invitation Secrets And Proofs

- Treat invitation tokens and OTP values as secrets.
- Keep the token only in the invitation route and required requests; never place it in storage, logs, analytics, toast messages, copied URLs, or unrelated navigation.
- Validate return paths as same-origin document-app paths. Reject absolute, protocol-relative, login, logout, and cross-app destinations unless generated by the approved handoff helper.
- Login is always required for secure invitation acceptance.
- User preference defaults are UI preselection only and never satisfy OTP, identity, ownership, or backend policy.
- Do not reveal whether a private document, collaborator, or invitation exists beyond the safe backend response.
- Prevent duplicate acceptance and treat timeouts as uncertain until the invitation is refetched.

## Signing And Workflow Integrity

- Preserve the backend sequence: draft -> finalise -> sign -> owner lock.
- Readiness comes from the documents readiness contract; do not infer it from profile fields or probe several services from the browser.
- Signing must use the local server orchestration path so signature creation and document evidence recording are coordinated.
- Never expose private keys, PIN derivation, signing secrets, raw certificate private material, or internal service credentials.
- Finalised, signed, and locked documents remain read-only through centralized policy even if stale UI state shows edit controls.
- After signing or locking succeeds, switch to read-only immediately and refetch authoritative state.
- Do not retry signing or locking automatically. A lost response creates an uncertain outcome that must be reconciled.
- QR codes and evidence blocks prove only what the backend verification contract supports; UI presence alone is not proof.

## Private Images And Downloads

- Profile images render through same-origin `/api/profile-image` and `UserAvatar` fallback.
- Never put raw presigned S3 profile-image URLs in shell or editor chrome DOM.
- Editor images must be uploaded through `api/documents` and stored in TipTap as stable document render URLs.
- Block `data:`, `blob:` persistence, embedded base64 payloads, raw bucket URLs, and private storage keys in document JSON.
- Validate URL schemes and origins through the shared image/link normalizers.
- Client checks for upload type, size, and dimensions supplement backend validation.
- Revoke temporary object URLs and clear previews after use.
- Downloads must use authorized endpoints, safe filenames, expected content types, and must not forward credentials cross-origin.

## Links And Imported Content

- Normalize editor links before they enter TipTap content.
- Allow only explicitly supported schemes; reject script, data, credential-bearing, protocol-relative, and malformed URLs.
- Open external links with `rel="noopener noreferrer"`.
- Treat DOCX/PDF text, styles, relationships, filenames, metadata, hyperlinks, and images as untrusted input.
- Do not render unsanitized imported HTML or arbitrary backend HTML with `dangerouslySetInnerHTML`.
- Import parsers must bound file size, decompression, page count, object count, and work where feasible.

## Public Verification

- Public verification displays authenticity and immutable evidence without exposing private document content, collaborators, emails, identifiers, storage URLs, or internal errors.
- Verification identifiers must be opaque and scoped for public lookup.
- Invalid, revoked, unknown, and service-unavailable results must be distinguishable without enabling enumeration.
- QR placement and payload semantics remain consistent across signed canvas, preview, PDF/DOCX output where supported, and public verification.
- Never treat a client-calculated hash or visual signature image as authoritative proof.

## Error, Logging, And Telemetry Safety

- Map backend failures to stable, minimal user-facing messages.
- Never render stack traces, database errors, internal policy reasons, cryptographic failures, headers, or raw response objects.
- Never log tokens, invitation secrets, OTPs, document content, private identifiers, image URLs, signature payloads, or cookies.
- Do not use `console.log` for production debugging.
- Client telemetry must be allowlisted and privacy-reviewed; never spread editor transactions, route params, or network objects into events.

## Browser Hardening

- Preserve the CSP and security headers in `next.config.ts`; new origins require explicit review.
- Do not add unsafe inline script/eval allowances to support an editor plugin.
- Keep secrets out of `NEXT_PUBLIC_*`; all prefixed variables are shipped to the browser.
- New third-party editor/export/runtime packages require supply-chain, CSP, privacy, and document-access review.
- Do not reintroduce third-party runtime pagination into the editable editor.

## Security Checklist

- Is the backend enforcing resource permission and workflow state?
- Can a token, private value, document body, or raw asset URL reach storage, URL, DOM metadata, logs, analytics, or an unintended origin?
- Are redirect and upstream origins fixed and validated?
- Does logout/session change clear document-scoped caches and transient data?
- Are signing, acceptance, finalise, and lock safe under duplicate submission and lost responses?
- Are finalised/signed/locked documents read-only across all view modes?
- Are temporary resources cleaned up on every exit path?
- Do `npm run check:security` and the relevant tests cover the change?
